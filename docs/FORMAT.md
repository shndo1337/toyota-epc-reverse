# Форматы данных Toyota EPC 2025.01

Описание получено исследованием файлов из `Toyota_EPC_2025_01.iso`; это не официальная спецификация Toyota.
Срезы — нулевые байтовые смещения, правая граница не включается.
В коде каждому файлу соответствует класс в [`epc/layout.py`](../epc/layout.py), имя класса указано в заголовке.

## Упаковка

ISO 9660 (8 630 177 792 байта) содержит установщик Inno Setup 6.3.0: EXE на 57 439 444 байта и пять BIN-частей.
Установщик не запускается: части распаковывает `7z`, а данные извлекает upstream `innoextract`
фиксированной ревизии (см. `scripts/build_innoextract.sh`).

Нужное дерево — `app/epcdata`:

| Каталог | Содержимое |
|---|---|
| `EU`, `GR`, `JP`, `US` | Каталоги рынков: модели, детали, разделы, иллюстрации |
| `FL/DM`, `FL/OV` | Записи конкретных автомобилей по номеру кузова и серийному номеру |
| `JPIO` | Аксессуары в CSV |

## Общие правила

- `*.ACD` хранятся с побайтовым XOR `0xC8`, длина не меняется. Изученные `*.DAT` читаются как есть.
- Текст в CP932. Сначала берётся байтовый срез, затем он декодируется: символ CP932 может занимать два байта.
- Записи фиксированной длины, без разделителей. Длина файла обязана быть кратна длине записи,
  иначе индексация останавливается.
- Месяцы хранятся как `YYYYMM`. Пустое значение, `000000` и `999999` означают открытый период (`null`).
- Большие таблицы отсортированы по ключу. Сервис читает их бинарным поиском через `mmap`
  и не копирует в SQLite: так устроены HNB, KPT, KRK, BZI, SIYOPT, KAKAKU, DAIHIN, CHOHIN и индексы изображений.

## Справочники рынка

### SHAMEI.ACD — 111 байт, XOR (`Catalogs`)

| Срез | Поле |
|---|---|
| `[3:23]` | Название модели |
| `[23:29]` | Код каталога, шесть символов; уникален только внутри рынка |
| `[29:79]` | Модельные коды через запятую, `#` — любой символ |
| `[79:85]`, `[85:91]` | Период выпуска |
| `[93:99]` | Месяц ревизии каталога |

### HINMEI01.DAT — 66 байт (`PartNames`)

`[0:6]` — PNC (код наименования детали), `[6:66]` — английское название.

### FIGMEI01.DAT — 124 байта (`FigureNames`)

`[0:4]` — код раздела, `[4:124]` — его название.

## Файлы каталога

Имена строятся из префикса и первых пяти символов кода: каталог `101510` → `101510/HNB10151.ACD`.

### HNB*.ACD — 122 байта, XOR (`PartRecords`)

| Срез | Поле |
|---|---|
| `[0:6]` | PNC, ключ сортировки |
| `[6:10]` | Группа EPC (`source_group`); `ZZZZ` и пустое значение подходят любой группе |
| `[10:22]` | Номер детали |
| `[22:24]` | Количество, строкой |
| `[24:30]`, `[30:36]` | Период применения |
| `[36:37]` | `1` — заголовок записи, `2` — продолжение |
| `[41:47]` | Группа применяемости (ссылка на KPT) |
| `[51:55]` | Группа диапазонов кузовов (ссылка на KRK) |

Продолжение (`[36:37] == 2`) относится к ближайшему предыдущему заголовку:
`[37:38]` — тип текста, `[38:40]` — номер фрагмента, `[40:122]` — текст.
Тип `1` содержит условия вида `1AZFE..ACV51`, остальные типы — примечания. Фрагменты отдаются API как есть.

Индексатор проверяет, что записи отсортированы по PNC: от этого зависит корректность бинарного поиска.

### FGI*.DAT — 22 байта (`FigureBindings`)

`[0:12]` — номер детали, `[12:18]` — PNC, `[18:22]` — код раздела.
Это единственная таблица, которая целиком копируется в индекс (`bindings`): по ней строится поиск по номеру,
названию, каталогу и разделу.

### KPT, KIG, KRK — правила применяемости

- **KPT*.DAT**, 9 байт (`ApplicabilityGroups`): группа `[0:6]`, номер строки KIG `[6:9]`.
- **KIG*.D01**, 82 байта (`CharacteristicLegend`): категория `[0:2]`, значение `[2:12]`.
  Номер строки (с единицы) — это индекс, на который ссылается KPT. **Он не совпадает с номером модели JOHO.**
- **KRK*.DAT**, 68 байт (`FrameRanges`): ключ `[0:4]`, начальный кузов `[8:15]` и серийный номер `[16:23]`,
  конечный кузов `[28:35]` и серийный номер `[36:43]`.

Проверка детали для автомобиля (`epc/services/fitment.py`):

1. месяц выпуска внутри периода записи HNB;
2. группа EPC совпадает или открыта;
3. значения KIG одной категории объединяются через OR, разные категории — через AND,
   и сравниваются с характеристиками модели из JOHO;
4. если у записи есть группа KRK, кузов и серийный номер должны попасть в один из диапазонов.

Текстовые примечания, цвет и опции автоматически не проверяются: они показываются пользователю.

### BZI*.DAT — 37 байт (`FigureImages`)

Раздел `[0:4]`, порядковый номер `[4:8]`, идентификатор иллюстрации `[8:15]`, период `[15:21]`–`[21:27]`.

## Модели и автомобили

### JOHOJP.ACD / JOHOKT.ACD — 186 байт, XOR (`Variants`)

JOHOJP используется на EU, GR и US, JOHOKT — в Японии.

| Срез | Поле |
|---|---|
| `[0:6]` | Код каталога |
| `[6:15]` | VIN-префикс; в Японии — type-код |
| `[15:35]` | Полная модель |
| `[35:41]`, `[41:47]` | Период выпуска |
| `[47:54]` | Кузов (frame) |
| `[54:58]` | Группа EPC |
| `[58:61]` | Номер строки модели |
| `[61:71]`, `[71:81]` | Характеристики `01` и `02` (двигатель) |
| `[81:186]` | Характеристики `03`–`23`, по 5 байт |

78 записей EU и US ссылаются на каталоги, которых нет в SHAMEI своего рынка, но которые есть в GR.
Они сопоставлены этим каталогам и перечислены в `/api/v1/import-issues`.

### FL/{DM,OV}/{кузов}/{серия}.ACD — 42 байта, XOR (`VehicleBlocks`)

Файл соответствует кузову и первым четырём символам серийного номера; `DM` — Япония, `OV` — остальные рынки.

| Срез | Поле |
|---|---|
| `[0:4]` | Первые четыре символа серийного номера |
| `[4:6]` | Последние три цифры, uint16 little-endian |
| `[6:10]`, `[10:23]` | Части модели: полная модель = кузов + `[6:10]` + `-` + `[10:23]` |
| `[23:25]` | Год, uint16 little-endian |
| `[25]` | Месяц |
| `[26:29]` | Цвет кузова |
| `[29:33]` | Салон |
| `[33:37]`, `[37:41]` | Группа и код спецификации (ключ SIYOPT) |

Полный VIN в этих файлах не хранится. Поиск по VIN: кандидаты моделей по префиксу из JOHO,
затем запись автомобиля по кузову и последним семи символам. Если записи нет, API возвращает
`catalog_candidates`, а не точное совпадение.

## Дополнительные таблицы

| Файл | Длина | Содержимое |
|---|---:|---|
| `SIYOPT/{группа}.DAT` | 12 | Ключ `[0:8]` (группа + код), категория `[8:10]`, значение `[10:12]` |
| `JP/KAKAKU.DAT` | 20 | Номер `[0:12]`, справочная цена JPY `[12:20]` |
| `DAIHIN.DAT` | 41 | Номер `[0:12]`, связанный номер `[17:29]` |
| `CHOHIN.DAT` | 43 | Номер `[0:12]`, связанный номер `[15:27]` |

Связанные номера отдаются с исходной записью: API не утверждает, что они взаимозаменяемы без условий.

## Иллюстрации (`ImageIndex`, `Thumbnails`, `Diagrams`)

`EMK*.IA0` и `IMAGEF.IA0` — индексы по 15 байт: идентификатор `[0:7]`, смещение и длина (uint32 LE, смещение с единицы).
`EMK*.DAT` хранит готовые PNG-миниатюры, `IMAGEF.DAT` — полноразмерные схемы:

- `[3]` — версия, поддерживаются `3` и `4`;
- `[11:13]`, `[13:15]` — ширина и высота, uint16 big-endian;
- `[15]` — `3`, сжатие CCITT Group 4;
- `[16:19]` — длина изображения, uint24 big-endian;
- `[21:21+длина]` — битовый поток.

Поток оборачивается в минимальный TIFF и декодируется libtiff через Pillow. Размеры и число пикселей ограничены,
другие версии формата не угадываются: API отвечает 422.

## JPIO

CSV в UTF-8 или CP932, от 12 до 17 столбцов: группа, номер строки, документ, заголовок, период,
название, номер, направления поставки, количество, примечания, модели, файл изображения.
Строки короче 12 полей (например, `CDINFO.CSV`) пропускаются. Исходный массив полей сохраняется в `raw_fields`.

## Проверяемость

`source_files` хранит путь, размер, SHA-256, длину записи и маску XOR каждого прочитанного файла.
Записи деталей идентифицируются как `РЫНОК:КАТАЛОГ:СМЕЩЕНИЕ`; по `/api/v1/applications/{id}` можно получить
исходные 122 байта после XOR. SHA-256 подтверждает соответствие конкретному локальному файлу,
а не подлинность издания.
